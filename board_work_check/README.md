# board-work-check

CLI-инструмент для старшего преподавателя: по одному JSON-бэкапу онлайн-доски
(Miro-подобный редактор) показывает, **вёл ли преподаватель работу с контентом**
или просто залил готовые материалы.

Детерминированные правила, без LLM и внешних API. Основной режим — анализ занятий:
фото результатов в интервале пары + последующее обновление ранее созданного материала.
Старый общий обзор доски доступен через `--analysis board`.

## Установка

Нужен Python 3.11+.

```bash
cd board_work_check
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -e .
```

Запуск без установки тоже работает:

```bash
python main.py backup.json                 # из корня проекта, без установки
python -m board_work_check backup.json     # после pip install -e . / с PYTHONPATH=src
```

## Куда класть файл бэкапа

Куда угодно — путь передаётся аргументом, копировать в проект не обязательно:

```bash
board-work-check "%USERPROFILE%\Downloads\data.json"
```

Если хочется держать бэкапы под рукой, есть папка `backups/` (она в
`.gitignore`, так что гигабайты JSON не попадут в репозиторий):

```bash
board-work-check backups/data1.json
```

## Запуск

```bash
board-work-check path/to/backup.json
```

Поддерживаются оба реальных варианта входа:

* «голый» JSON бэкапа (объект с `boardName`, `version`, `objects`, `comments`);
* ZIP-архив экспорта (`.holst`/`.rtb`), внутри которого лежит `data.json`.
  Архив читается целиком только по нужной записи, ассеты (png/docx/pptx)
  не распаковываются.

```bash
board-work-check board.holst
```

Полезные варианты:

```bash
board-work-check backup.json --output json                 # JSON в stdout
board-work-check backup.json --save-json report.json       # + сохранить отчёт
board-work-check backup.json --verbose                     # диагностика в stderr
board-work-check backup.json --analysis board               # старый общий обзор
board-work-check backup.json --follow-up-hours 24           # окно обработки после пары
board-work-check backup.json --config config.yaml          # свой конфиг
board-work-check backup.json --no-color                    # без ANSI-цветов
```

Коды выхода: `0` — успех, `1` — файл не удалось разобрать (даже после
восстановления), `2` — файл/путь/конфиг недоступны.

## Пример старого общего вывода

Подробный общий отчёт сохранён для совместимости и доступен через
`--analysis board`. По умолчанию CLI выводит только результаты, сгруппированные по занятиям.

В основном режиме `--output json` печатает `board`, `teacher_author`, `lessons` и
`limitations`. Для прежнего общего отчёта используйте `--analysis board`: он содержит
`import_mode`, `signals`, `frames_with_edits`, `verdict`, `parser.warnings`, `thresholds`.

### Анализ занятий

По умолчанию используются семь локальных интервалов (таймзона из конфига):
08:30–10:00, 10:15–11:45, 12:05–13:35, 14:05–15:35, 15:55–17:25,
17:40–19:10, 19:20–20:50. Дата берётся из `created.t` изображения. Изображение,
созданное во время пары, считается кандидатом результата студента, но само по себе
не считается проверкой. Признак проверки — обновление объекта, созданного до начала
пары, автором-преподавателем после появления изображения и в течение 24 часов после
конца пары (окно меняется через `--follow-up-hours`). Новое изображение не является
старым материалом.

Автор преподавателя выводится эвристически по правкам старого контента и неимпортным
добавлениям; загрузки изображений и массовый импорт не повышают рейтинг. Для разных
досок автор может отличаться. При сомнении можно задать `analysis.teacher_author_id`.
Названия вроде `Практика 18-20` распознаются как диапазон занятий, но не заменяют
дату: дата и время берутся из временных меток. Фреймы с признаками пакетного импорта
помечаются `not_analyzable_imported`, а не как отсутствие работы.

Snapshot не содержит историю версий или diff содержимого. Поэтому результат — это
признак обновления, а не доказательство смысловой проверки; уверенность ограничена.


## Как это считается

### 1. Текст объектов

`jsonState.children` в бэкапе — это **строка**, внутри которой лежит JSON.
Она разбирается, из всех узлов `paragraph -> children -> text` собираются
сегменты, склеиваются через пробел и нормализуются (trim + collapse
whitespace). Пустой результат — `None`. Битый `jsonState` не роняет разбор.

### 2. Режим доски (`import_mode`)

Считается по `created.t`:

| доля самого частого `created.t` | режим |
|---|---|
| `>= 0.9` | `post_import` — доска загружена одним пакетом |
| `<= 0.3` и уникальных значений `>= max(5, 10% объектов)` | `full` — время создания реальное |
| иначе | `mixed` — смешаны импорт и ручная работа |
| нет валидных `created.t` | `unknown` |

* `post_import`: `created.t` — это момент импорта, а не создания. Анализ только
  по `updated`, в отчёте обязательная строка про недоступность истории.
* `full`: можно использовать и разброс `created.t`.
* `mixed`: результат помечается как требующий ручной проверки, уверенность
  понижается до `medium`.

### 3. Сигналы

Сильные: `n_real_edits` (объектов с `updated.t - created.t > 5 мин`),
`n_objects_updated`, `frames_with_edits`, `n_unique_updated_authors`,
`n_comments`, `created_spread_hours` (только не в `post_import`).

Слабые: заполненные `table-cell`, стикеры с текстом, `mind-map-node` с
текстом, `drawing` (штрихи свободного пера), `image` (отдельно — изображения
с «фото»-именами).

`drawing` — это не картинка, а один штрих свободного пера: рукописная
страница даёт сотни таких объектов. Картинки и сканы — это `image`, их
счётчик печатается отдельной строкой, чтобы числа не путались.

Антипаттерны: `file` (docx/pptx/pdf), пустые стикеры, массовое одинаковое
`created.t`.

Вложенность учитывается по `parentId` на любую глубину:
`table-cell -> table -> frame`, а также объекты внутри `group`. Фрейм
считается затронутым, если «настоящая» правка есть у любого его потомка.

### 4. Вердикт

```text
no_work_detected : n_real_edits == 0 и нет заполненных ячеек, рисунков,
                   стикеров с текстом
work_detected    : n_real_edits >= 3
                 | (заполненные ячейки > 0 и n_real_edits > 0)
                 | (режим full и created_spread_hours > 24)
ambiguous        : остальное
```

Уверенность: `high` — 3+ сильных сигнала, однозначный режим, файл не обрезан;
`medium` — 1–2 сильных сигнала или режим `mixed`; `low` — только слабые
сигналы или 3+ предупреждения.

### 5. Обрезанный файл

Если `json.loads` падает, парсер вручную проходит текст со счётчиком `{}`/`[]`
(с корректной обработкой строк и экранирования), находит последний полностью
закрытый объект в массиве `objects`, обрезает файл по нему и закрывает `]}`.
Результат: `is_truncated = true`, предупреждение в отчёте, код выхода `0`.
Скобки внутри текстов стикеров разметку не ломают.

## Конфигурация

Значения по умолчанию зашиты в код; `config.yaml` — необязательный override.

```yaml
analysis:
  threshold_real_minutes: 5
  import_share_threshold: 0.9
  full_share_threshold: 0.3
  unique_created_min: 5
  classification:
    n_during_min: 3
    confidence_high_min_signals: 3
    warnings_low_threshold: 3
  timezone: "Asia/Yekaterinburg"
  teacher_author_id: null  # необязательный override автора преподавателя
  suspicious_image_name_patterns: ["screenshot", "photo", "фото", "скрин"]
```

Файл валидируется pydantic: неизвестный ключ, отрицательный порог или
перепутанные местами `full_share_threshold`/`import_share_threshold` дают
понятную ошибку и код выхода `2`.

## Ограничения

* **Один снимок.** Инструмент не восстанавливает хронологию: он видит только
  итоговое состояние и метки `created`/`updated`. Открытие доски без правок
  нигде не логируется.
* **Импорт.** При `post_import` история до импорта недоступна: всё, что было
  сделано до загрузки, не видно.
* **Обрезка.** В обрезанном файле часть объектов теряется: сигналы могут быть
  занижены, о чём явно сказано в отчёте.
* **Содержание не оценивается.** Считается только наличие текста/правок, а не
  его качество или правильность.
* **Вложения не открываются.** 51 docx/pptx считается как факт загрузки файла,
  но их содержимое не анализируется.
* **Авторы.** `created.a` и `updated.a` не смешиваются: это могут быть разные
  люди, и «автор правок» — только `updated.a`.

## Что добавлено к постановке

* Поддержка ZIP-экспорта (`.holst`) — реальный файл доски приходит именно так.
* Текст у стрелок (`texts`) как резервный источник, если `jsonState` нет.
* Атрибуция правок через `group` и любые промежуточные контейнеры.
* Сигналы `n_frames_total`, `n_frames_without_edits`, `n_images_photo_like`,
  `n_objects_created_same_ms` и порог в `Signals` — чтобы отчёт печатал
  «На 46 из 55 фреймов нет правок» и «> 5 мин» без доступа к конфигу.
* Устойчивость вывода к кодировке консоли (cp1251/cp866): непечатаемые
  символы заменяются, а не роняют команду.
